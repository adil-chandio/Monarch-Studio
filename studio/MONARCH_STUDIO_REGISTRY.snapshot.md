## What this is
One registry for every Monarch editing / animation workflow (style). One workflow = one `WF-nn` code, one unique
name, one unique resume key, one section on each of the four platforms (Notion, Linear, Google Drive, Google Docs),
and every section links to the same workflow's sections on the other three. When a workflow name or resume key is
mentioned on any platform: open the registry there → find the row → follow its hub link → continue inside that
workflow only.

## Resume protocol (any platform → the right workflow)
1. A workflow **name**, **resume key** or **trigger word** is given (e.g. "SHADEGO <topic>" → WF-01; "best video reel editing" → WF-01; "TABAHI ACTIVATE" → WF-02; "NOIRGO <topic>" → WF-03).
2. Open the registry on whatever platform is at hand; find the row by WF code / name / key — never by the bare phrase
   "Monarch Stickman Animation" (it belonged to two workflows before 2026-10-09; see the collision note).
3. Follow that row's hub link on the same platform: Linear project body §0 → resume issue newest comments ·
   Notion hub top callouts → Doc 00 · Drive folder → `RESUME_STATE.md` · Google Doc HUB → "Current state".
4. Follow the hub's own resume order and continue **inside that workflow only**. Record every change back into that
   workflow's sections; a registry row changes only when status / links / open items change.

## How to add a workflow (WF-03, …) — checklist
1. Define: WF code, unique name, unique resume key, style/engine one-liner, local root `workflows/<slug>/`
   (never mixed with another workflow's sources). `python3 studio/new_workflow.py --wf 03 --name "…" --key "…" --style "…"`
   scaffolds the folder from `studio/WORKFLOW_TEMPLATE.md` and appends the row above (fill the URLs after steps 2–5).
2. **Google Drive:** folder `MONARCH STUDIO / WF-nn · Name /`; every deliverable goes there with md5 recorded.
3. **Google Docs:** `WF-nn · Name — HUB` inside that folder (identity · key · 4 links + registry · resume order ·
   current state · open items · rules).
4. **Notion:** Projects-DB page `WF-nn · Name` (hub) with a top LINKS callout; its Docs in the Docs DB (Doc 00 =
   current state); row in the **Workflows** DB with all four URLs + key + status + open items, related to the page.
5. **Linear:** project `WF-nn · Name` (team MON): body §0 = current state + LINKS; issue `00 · RESUME KEY …` with
   attachments (Notion hub, Drive folder, Google Doc HUB); STATE comment on it after every working turn.
6. **Registry rows:** Linear registry body + MON-55 · Google Doc registry · this file · Notion Workflows DB.
7. **Local:** `workflows/<slug>/RESUME_STATE.md` + `HUB.md` + `CHECKLIST.md`; upload `RESUME_STATE.md` to the
   workflow's Drive folder at the end of every working turn.
8. **Round-trip test:** from each of the four platforms the workflow's section links to the other three and the
   registry row reaches the hub; reply with all ids/URLs.

## Conventions
`WF-nn · Name` identical on every platform · WF codes never reused · status Active / Parked / Legacy / Planned ·
per turn inside a workflow: deliverables → its Drive folder (md5, same turn); state → local `RESUME_STATE.md`
(newest block on top) + Linear resume-issue STATE comment + Notion Doc 00 top callout + Google Doc HUB "Current
state"; status change → registry row on all four platforms · never write one workflow's facts into another's
sections; ambiguous name → stop and resolve by WF code + id first.
